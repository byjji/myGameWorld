# Phase 4 — 줄넘기 + 첫 실기 검증

> 참조: PROJECT.md §5-1, §9-3, §10

## 목표

**첫 수직 슬라이스.** 대기 → 캐릭터 선택 → 동작 시연 → 카운트다운 → 플레이 → 결과가 한 줄로 이어진다.

줄넘기를 먼저 만드는 이유는 게임이 쉬워서가 아니라, 이 한 판에서
**통신 지연 · 센서 권한 · HTTPS · TV 연결 · 조카의 실제 반응**이 전부 한꺼번에 검증되기 때문이다.

## 산출물

- `js/games/jumprope.js` — phase3에서 정의한 미니게임 인터페이스 구현
- `js/gfx.js` — 오프스크린 프리렌더 · 파티클 풀 · 화면 흔들림. phase1 예산을 한 곳에서 지킨다
- `js/sfx.js` — WebAudio 합성 효과음. 에셋이 없어도 피드백이 비지 않게
- 줄넘기 스프라이트/배경 에셋 — **임시 도형이다.** 줄은 프리렌더 곡선, 캐릭터는 `js/chars.js`의 사각형.
  실제 2.5D 스프라이트가 나오면 그리는 자리만 갈아끼운다
- 결과 화면 (시상대, 폭죽, 점수 획득 애니메이션)
- `docs/playtest-1.md` — 첫 실기 플레이테스트 기록 **(빈 양식. 조카 집에서 채운다)**

## 작업 항목

### 게임

- [x] **캐릭터 제자리 고정, 줄만 회전.** 카메라 이동·스크롤 없음
- [x] 배경은 정지 화면 한 장 (TV 부하 최소)
      *사각형 세 개. 오프스크린조차 쓰지 않는다*
- [x] 줄 회전 애니메이션 — 미리 그린 스프라이트 시퀀스 사용, 실시간 곡선 계산 금지
      *`js/gfx.js`의 오프스크린 시트에 16프레임 프리렌더. 매 프레임은 blit 한 번*
- [x] 판정 창 — 줄이 발밑을 지나는 시점 ± 허용 오차. **오차를 넉넉하게.** 5세 기준
      *±0.42초. 한 바퀴(1.7초)의 절반 가까이. 창이 한 바퀴를 다 먹지 않게 상한만 걸었다*
- [x] `motion.js`의 점프 이벤트만 구독. 다른 동작은 무시
- [x] **줄 속도를 느리게 시작해 10개마다 조금씩 가속**
      *1.70초에서 시작, 10개마다 0.09초씩, 0.85초가 하한*
- [x] 실패 시 게임오버 없음 — 캐릭터가 줄에 걸리는 짧은 연출 후 즉시 재개
      *0.7초. **타이밍이 어긋난 점프는 아예 실패로 치지 않는다** — 한 바퀴를 통째로
      놓쳤을 때만 걸린다. 일찍 뛰었다고 벌하면 5세는 몇 번 만에 그만둔다*
- [x] 성공 카운트 = 점수. 연속 성공 콤보 연출
- [x] **한 판 90초** 또는 목표 개수 도달 시 종료 (60개)
- [ ] 통신 지연 보정 — 폰에서 판정한 시각을 메시지에 실어 보내고 TV에서 보정할지 검토 (실측 후 결정)
      *보정하는 자리는 만들어 뒀다 (`js/tuning.js` `JUMP_LAG_MS`, 줄넘기가 그만큼 시계를 되돌려 판정).
      **값은 0이다.** 추측한 숫자를 넣으면 실제 지연이 얼마인지 영영 모르게 된다.
      타임스탬프를 메시지에 싣는 방식은 실측 후에 결정한다*

### 연출·사운드

- [x] 점프 성공 시 효과음 + 폰 진동. **동작 중에는 폰 화면을 볼 수 없다**
      *소리는 TV(`js/sfx.js`, WebAudio 합성 — 에셋 미정이라 오실레이터로).
      진동은 TV가 보낸 `fx`를 폰이 받아서 낸다. 서버가 폰에 자리(`you`)를 알려주므로
      특정 폰만 떨게 할 수 있다*
- [x] 10개 단위 달성 연출
- [x] 결과 화면 — 시상대 + 폭죽 + 점수 카운트업
      *폭죽은 `gfx.Particles`. 개수 상한 `MAX_PARTICLES`를 넘지 않는다*

### 실기 준비

전부 조카 집에서만 가능하다. 양식은 `docs/playtest-1.md`에 만들어 뒀다.

- [ ] Netlify 배포 후 조카 집 TV에서 실제 URL로 접속
- [ ] fps 오버레이(`?fps=1`) 켜고 한 판 — 프레임 수를 사진으로 기록
      *개발 PC 크롬 기준 60fps, `draw 1 · cost 2/150 · text 3/12`. TV 기준은 실기에서*
- [ ] (선택) `tv-bench.html`이 있으면 5분 내로 한 번 돌린다
- [ ] 폰 2대(어른 + 조카) 접속 시 동작 확인 — 범위는 phase9에서 확정, 여기서는 깨지지 않기만 하면 됨
      *두 명 각자 점수가 따로 세지는 것까지는 시험에서 확인 (`test/games-test.js`)*

## 완료 기준

**전부 조카 집에서만 확인된다.** 게임은 다 만들었고 확인만 남았다.
개발 PC에서는 진짜 릴레이 서버를 거쳐 대기 → 캐릭터 선택 → 시연 → 캘리브레이션 →
카운트다운 → 플레이 → 결과가 한 줄로 이어지는 것까지 확인했다.

- [ ] **조카 집에서 실제로 한 판을 끝까지 플레이했다**
- [ ] 점프 판정이 조카의 실제 점프 높이로 안정적으로 잡힌다 (어른 기준으로 맞추면 안 잡힌다)
- [ ] 30fps가 실기에서 유지된다 — **phase1 전제의 첫 실검증.** 미달이면 `js/config.js` 상한을 낮춰 재확인 (게임 로직은 손대지 않는다)
- [ ] 폰 화면을 보지 않고 TV만 보며 플레이한다
- [ ] `docs/playtest-1.md`에 아래가 기록됨
  - 조카가 폰을 실제로 쥔 방법 (예상과 다를 것)
  - 뛰는 범위·강도
  - 흥미를 잃은 지점과 시각
  - 어른의 개입이 필요했던 지점
  - 다시 하자고 했는지 여부

## 검증 방법

플레이 장면을 옆에서 영상으로 찍는다. 표정과 손 위치는 나중에 기억나지 않는다.
플레이 후 `motion.js` 임계값을 실측 기반으로 조정하고 다시 한 판.

## 리스크

- **여기서 나오는 문제가 이 프로젝트의 실제 문제다.** 예상 못 한 항목이 나오면 PROJECT.md를 고치고 이후 phase 계획을 재조정한다
- 조카가 폰을 가슴에 대지 않고 손에 들고 흔들 가능성 → 판정 임계값 또는 쥐는 방식 안내 연출로 대응
- 지연이 체감되면 phase2 인프라로 되돌아간다. 게임 로직으로 덮지 않는다
