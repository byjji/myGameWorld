# Phase 2 — 릴레이 서버 + 배포 인프라

> 참조: PROJECT.md §1, §2, §8, §9-2

## 목표

폰과 TV가 서로 다른 집에 있어도 메시지가 오가는 경로를 만든다.
서버는 **게임 로직을 갖지 않는다.** 방 단위로 메시지를 그대로 넘기는 릴레이일 뿐이다.

정적 파일은 Netlify, WebSocket만 NAS. 우리 집 업로드 대역으로 에셋을 매번 내보내지 않기 위함.

## 산출물

- `server/rooms.py` — 방 규칙. 소켓을 모르는 순수 로직이라 서버 없이 시험할 수 있다
- `server/main.py` — FastAPI, WS 릴레이. rooms.py를 소켓에 붙이는 어댑터
- `server/Dockerfile`, `docker-compose.yml` — Synology NAS Docker 배포용
- `netlify.toml`, `netlify-build.sh` — 정적 배포 설정. 저장소 전체가 아니라 배포에 필요한 것만 올린다
- `echo_1.html` (`/echo`) — 통신만 떼어 보는 진단 페이지. 연결·왕복·RTT·끊김 횟수
- `test/relay-test.py` — 방 규칙 + 실제 WebSocket 왕복 시험
- `docs/deploy.md` — NAS·DDNS·인증서·Netlify 절차와 확인 순서
- HTTPS 도메인 (DDNS + Let's Encrypt), `wss://` 접속 확인 ← 사람이 계정 앞에서 해야 하는 부분

## 작업 항목

### 서버

- [x] `WS /ws/{code}?role=tv|play` 엔드포인트
- [x] 방 상태는 **서버 메모리 딕셔너리**. DB 없음. 재시작 시 방 소멸 — 정상 동작으로 취급
- [x] `{"t":"create"}` — 방 생성 + 4자리 코드 발급
      *방은 TV가 접속하는 순간 만들어진다. `create`는 코드를 다시 알려줄 뿐 방을 새로 만들지 않는다 —
      net.js가 재접속 때마다 `create`를 보내기 때문에, 만들어버리면 방이 매번 갈린다*
  - [x] **코드 문자는 `2,3,4,5,8,9`만 사용** (0/6, 1/7 혼동 방지, PROJECT.md §7)
  - [x] 중복 코드 회피
- [x] `{"t":"join"}` — 폰 입장, TV에 접속 알림 브로드캐스트
- [x] 릴레이 규칙: 폰 → 같은 방 TV, TV → 같은 방 전체 폰. 서버는 페이로드를 해석하지 않는다
      *폰 메시지에는 서버가 `from`(p1..p4)을 찍는다. 폰이 붙인 `from`은 덮어쓴다 — 남인 척할 수 없어야 한다*
- [x] 존재하지 않는 코드로 접속 시 명시적 거부 응답
      *`{t:'err'}`를 보내고 닫는다. 소켓 오류와 구분돼야 폰이 "틀린 코드"를 보여줄 수 있다 (`js/play.js`)*
- [x] 연결 종료 처리 — 폰 이탈 시 TV에 통지, TV 이탈 시 방 정리
      *TV 이탈은 60초 유예 후 정리. 즉시 지우면 잠깐 끊긴 사이에 방 코드가 바뀌어 조카가 다시 입력해야 한다*
- [x] 빈 방 타임아웃 정리 (메모리 누수 방지)
- [x] `tilt` 같은 고빈도 메시지가 큐에 쌓이지 않도록 백프레셔 확인
      *`tilt`/`state`는 최신값으로 덮어쓰고 `motion` 같은 사건은 보존한다. 2000개를 밀어 넣어도 큐 길이 1*
- [x] 헬스체크 엔드포인트

### 인프라

인프라 항목은 NAS·도메인·Netlify 계정 앞에서 사람이 해야 한다. 절차는 `docs/deploy.md`에 적어뒀고,
코드로 준비할 수 있는 것(Dockerfile, compose, netlify.toml, 빌드 스크립트)은 전부 만들어 뒀다.

- [ ] NAS Docker 컨테이너 기동 + 재부팅 시 자동 시작
      *`server/Dockerfile` + `docker-compose.yml` 작성 완료(`restart: unless-stopped`). NAS에서 기동·재부팅 확인 남음*
- [ ] DDNS 설정
- [ ] Let's Encrypt 인증서 발급 + 자동 갱신
- [ ] 리버스 프록시에서 WebSocket 업그레이드 헤더 통과 확인
- [ ] Netlify에 정적 파일 배포, 루트(`/`)에서 **TV 화면**이 열리도록 (리모컨 입력 최소화, PROJECT.md §12)
      *`netlify.toml` + `netlify-build.sh` 작성 완료. 루트→TV, `/p`→폰, `/echo`, `/bench` 리다이렉트.
      로컬에서 빌드 스크립트 실행해 dist 구성 확인. 실제 배포는 계정 연결 후*
- [ ] 도메인 확정 — 리모컨으로 칠 수 있게 최대한 짧게
      *정해지면 `js/net.js`의 `defaultUrl()` 기본 릴레이 호스트도 같이 바꾼다*
- [ ] 정적 페이지(HTTPS)에서 `wss://` NAS 접속 시 혼합 콘텐츠 차단 없는지 확인

## 완료 기준

아래는 전부 **집 밖 네트워크와 실기**가 있어야 확인된다. 서버 코드는 준비됐고 확인만 남았다.

- [ ] 외부망 폰과 개발 PC 브라우저 두 대가 같은 코드로 붙어 메시지가 왕복한다
      *로컬(127.0.0.1)에서는 통과. 실제 브라우저 두 탭으로 TV↔폰 왕복과 `from` 스탬프까지 확인했다.
      외부망은 배포 후*
- [ ] **조카 집 TV 브라우저에서 `wss://` 연결 성공** (TV 브라우저의 인증서 검증이 가장 까다롭다)
- [ ] 왕복 지연 측정 — ping/pong 라운드트립 30~50ms 범위 확인. 넘으면 원인 규명 후 진행
      *측정 경로는 동작한다(로컬 RTT 중앙값 0.5ms). 비교할 값은 외부망에서만 나온다*
- [ ] NAS 재부팅 후 자동 복구 확인

## 검증 방법

- 에코 테스트 페이지로 폰↔TV 메시지 왕복 및 RTT를 화면에 표시 — **`echo_1.html` (`/echo`)**
- 30분 연속 접속 유지 테스트 (프록시 idle timeout으로 끊기는지 확인)
- 폰 네트워크를 Wi-Fi ↔ LTE로 전환했을 때 재접속 동작 확인

배포 없이 지금 돌려볼 수 있는 것:

```
python test/relay-test.py          방 규칙 50항목 + 실제 WebSocket 왕복 10항목
GP_STATIC=. python server/main.py  로컬에서 정적+릴레이를 한 포트로 띄운다
  → http://127.0.0.1:8000/tv/index.html  과  /play/index.html
```

`GP_STATIC`은 개발용이다. 평시에는 비워둔다 — 정적 파일은 Netlify 몫이다 (PROJECT.md §1).

## 리스크

- 통신 계층의 실제 검증은 phase4(줄넘기 실기)에서 끝난다. 여기서는 "붙는다"까지만 보증한다.
- TV 브라우저가 구형 TLS만 지원할 가능성 → 인증서·프로토콜 설정에서 하위 호환 확인 필요.
- 프록시 idle timeout이 짧으면 게임 중 끊긴다 → keepalive ping 주기 설정.
