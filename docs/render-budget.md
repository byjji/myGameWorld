# 렌더링 예산

> phase1 산출물. 코드 상수는 `js/config.js`, 계측은 `js/fps.js`.
> 근거 문서는 `PROJECT.md` §2 렌더링 제약.

## 전제

**조카 집 TV에서 30fps 안정 유지는 가능한 것으로 판단한다.**

성능 실측을 개발의 차단 조건으로 두지 않는다. 여기 적힌 숫자는 측정 결과가 아니라 **먼저 정해놓은 상한**이다.
목적은 추측을 없애는 것이 아니라 **추측을 한 곳에 모아 나중에 한 번에 고칠 수 있게** 하는 것.

전제가 틀렸다고 판명되면 `js/config.js`의 숫자만 낮춘다. 게임 로직은 건드리지 않는다.
그러려면 게임 코드에 같은 숫자가 중복돼 있으면 안 된다. **모든 렌더링 수치는 `js/config.js`를 참조한다.**

전제 검증 시점: **phase4 실기 플레이테스트.** 게임과 함께 확인한다.
`tv-bench_1.html`은 그 방문 때 5분 안에 곁다리로 돌리는 선택 작업이다.

## 프레임

| 항목 | 값 | 이유 |
|---|---|---|
| 목표 프레임 | **30fps** | 60fps 전제로 만들면 실기에서 게임 속도가 절반이 된다 |
| 프레임 예산 | 33.3ms | 1000 / 30 |
| 실작업 목표 | **20ms** | TV 브라우저 지터 대비 40% 여유 |
| 경고 임계 | 40ms | 넘으면 화면에 붉은 테두리 |
| deltaTime 상한 | 0.1s | 탭 전환·정지 후 복귀 시 한 프레임에 시간이 몰려 캐릭터가 벽을 뚫는 것 방지 |

모든 움직임은 `deltaTime` 기반. 프레임 수를 전제한 코드 금지.

## 캔버스

| 항목 | 값 |
|---|---|
| 내부 해상도 | **1280 × 720** |
| 표시 | CSS로 화면 채우기 (1080p 실시간 채우기는 부담) |
| devicePixelRatio | **곱하지 않는다.** backing store를 키우면 그대로 부하 |
| 안전영역 | **5%** — 유효 영역 1152 × 648, 원점 (64, 36) |

구형 TV는 가장자리가 잘린다. 모든 UI는 안전영역 안쪽. 특히 방 코드와 점수.

## 그리기 예산 (프레임당)

가중 합 상한 **150**. 호출 종류별 가중치:

| 종류 | 가중치 |
|---|---|
| 원본 크기 `drawImage` | 1 |
| 스케일링 (원근) | 1.5 |
| 알파 블렌딩 | 2 |
| 회전 | 2 |

즉 원본 크기만 그리면 150장, 전부 알파면 75장.

| 별도 상한 | 값 | 이유 |
|---|---|---|
| 알파 스프라이트 동시 | 60 | 블렌딩은 채우기 비용이 붙는다 |
| 파티클 동시 | **24** | 특히 블록깨기 코인 연출 |
| `fillText` 호출 | 12 | TV는 폰트 래스터라이즈가 비싸다. 반복 글자는 오프스크린에 그려두고 blit |
| 오프스크린 캔버스 | 8장, 한 변 1024 이하 | 넘기면 TV 메모리를 밀어낸다 |
| 배경 레이어 | 3 | 정지 배경은 1장, 스크롤은 타일 반복 |

숫자의 출처: 프레임당 20ms 작업 예산 ÷ TV 내장 브라우저의 `drawImage` 1회 추정 비용(0.06~0.12ms).
**추정치다.** 실기에서 어긋나면 이 표와 `js/config.js`를 같이 고친다.

### 도형 채우기는 이 표에 없다 (phase8에서 드러남)

여기 있는 상한은 전부 `drawImage`와 `fillText` 기준이다. 미니게임 넷은 배경과 캐릭터를
그림으로 그렸으므로 그것으로 충분했다. **레이싱은 다르다** — 도로가 그림이 아니라
사다리꼴 채우기 수백 번이다.

개발 PC에서 잰 레이싱 한 프레임 (`js/pseudo3d.js` 기본값, 들판 코스):

| 호출 | 횟수 | 이 표의 상한 |
|---|---|---|
| `fill` (사다리꼴) | 126 | 없음 |
| `fillRect` (풀밭 가로줄) | 73 | 없음 |
| `drawImage` | 9 | 150 |
| `fillText` | 3 | 12 |

**아래 둘은 넉넉하고 위 둘은 재본 적이 없다.** TV에서 이 200번이 버티는지가
레이싱 프레임의 전부다. 안 버티면 `road.DRAW_SEGS`를 낮춘다 — 그리는 세그먼트 수가
그대로 채우기 횟수다. 측정은 `/road` (`tools/road-bench_1.html`), 절차는
`docs/playtest-racing.md` 1장.

## 금지 항목

| 금지 | 대체 |
|---|---|
| **Three.js / WebGL** | 2D Canvas + 원근 스프라이트로 2.5D 표현 |
| **`shadowBlur` / `shadowColor`** | 미리 그린 그림자 스프라이트 |
| **`ctx.filter` / CSS `filter: blur`** | 흐림이 들어간 이미지를 미리 만들어 둔다 |
| **대량 파티클** | 개수 제한 + 미리 그린 애니메이션 스프라이트 시퀀스 |

WebGL은 지원되더라도 쓰지 않는다. 컨텍스트를 얻는 것과 프레임이 나오는 것은 별개다.

## 문법 수준

**기반 계층(`js/config.js`, `js/fps.js`)은 ES5로 작성한다.**

파일이 작아 ES5로 써도 비용이 없고, 구형 webOS의 파싱 실패 위험을 기반에서 제거할 수 있기 때문이다.
기반이 파싱되지 않으면 화면에 아무것도 안 나와 원인 파악조차 어렵다.

게임 코드의 ES6 사용 가부는 `tv-bench_1.html`의 `ES6 파싱` 항목으로 판정한다.
- `가능`이면 게임 코드는 ES6 사용
- `실패`면 전체 ES5 유지

**ES module (`type="module"`)은 쓰지 않는다.** 일반 `<script>` 태그 + 전역 `GP` 네임스페이스.
빌드 단계가 없는 바닐라 JS이므로 문법 하향이 필요해졌을 때 수작업 범위를 줄이려면 모듈 경계를 얕게 둬야 한다.

## 계측

`js/fps.js`가 `ctx.drawImage` / `ctx.fillText`를 감싸 호출 수를 센다.

- 켜기: 주소 뒤에 **`?fps=1`**
- 꺼져 있으면 래핑조차 하지 않는다. 평상시 부하 0
- 표시: fps / 프레임 ms / 구간 최악 ms / `drawImage` 수 / 가중 비용 / 예산 초과 누적
- 예산 초과 시 붉은 테두리 + `SPRITE BUDGET OVER` 표시

**TV 브라우저에는 개발자도구가 없다.** `console.log`에 의존하지 않는다. 모든 진단은 화면에 그린다.
